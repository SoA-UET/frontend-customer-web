# H31 Group

This is the group of HTTP APIs between
the **Partner Portal web frontend**
and [S13 - Partner Consultation Service](../services/partner/S13_Partner_Consultation_Service.md).

This API group supports the follow use cases:

- TP-17: Tiếp nhận yêu cầu tư vấn văn bản chuyển từ Core
- TP-18: Tiếp nhận cuộc gọi thoại chuyển từ Core
- TP-21: Xem lịch sử các phiên tư vấn được chuyển tiếp từ Core

The APIs are designed following RESTful
principles (except Socket.IO details)
and focus on the listed use cases.

## Regarding HTTP API(s)

Endpoints denoted with "AUTH"
means that it must be authenticated
using JWT.

[How to verify JWTs](../auth/VERIFY.md)

## H31

This API is based on HTTP (RESTful).

## Overview

## Design Principles

- REST (HTTP) for:
  - resource management
  - message submission
  - history retrieval
  - ratings

- Socket.IO for:
  - real-time audio streaming
  - real-time text streaming

## HTTP Endpoints

Endpoints denoted with "AUTH"
means that it must be authenticated
using JWT.

[How to verify JWTs](../auth/VERIFY.md)

### GET AUTH /api/v1/conversations

Get all past conversations.

Response body:

```ts
{
    "content": Array<{
        "id": string,
        "title": string,
    }>
}
```

Note that via this API, new conversations
cannot be created - because conversations
are created by S01 (Core) when forwarding
requests arrive.

### GET AUTH /api/v1/conversations/{conversation_id}

Get details of a conversation.

Response body format:

```ts
{
    "content": {
        "id": string, // ID of the conversation
        "title": string, // e.g. "Tư vấn gói cước"
        "customer_id": string, // ID of the currently authenticated customer
        "status": string, // one of `AI_AGENT_TEXTING`, `AI_AGENT_CALLING`, `FORWARDING`, `HUMAN_AGENT_TEXTING`, `HUMAN_AGENT_CALLING`.
        "partner_id": string, // ID of the forwarded partner.
        "customer_satisfaction": number, // ranging from 1 to 5.
        "summary": string, // the conversation summary up to this point.
        "created_at": datetime, // e.g. "2025-12-08T10:30:00Z"
        "updated_at": datetime
    }
}
```

### POST AUTH /api/v1/conversations/{conversation_id}/messages

Send a text message from consultant (human agent)
to customer.

Request body format:

```ts
{
    "content": string, // e.g. "Gói cước SD-70 có giá 70.000 VNĐ bạn nhé."
}
```

Response body format:

```ts
{
    "content": {
        "id": string, // ID of the message,
        "conversation_id": string, // ID of the conversation which this message belongs to
        "sender_type": string, // The sender type, one of: `CUSTOMER`, `AI_AGENT`, `HUMAN_AGENT`. Here it would be `HUMAN_AGENT`.
        "sender_id": string, // The sender ID - this only exists when sender_type is HUMAN_AGENT (here it exists).
        "sender_name": string, // The sender name - this only exists when sender_type is HUMAN_AGENT (here it exists).
        "content": string, // e.g. "Gói cước SD-70 có giá 70.000 VNĐ bạn nhé."
        "created_at": datetime, // Message creation time, e.g. "2025-12-08T10:30:00Z"
    }
}
```

### GET AUTH /api/v1/conversations/{conversation_id}/messages

Retrieve full message history of a conversation,
with pagination.

Possible (all optional) request query params:

- `pageNumber` - number
- `pageSize` - number
- `search` - string; if specified, only returns messages in this conversation each of which has content including this search string.

Response body:

```ts
{
    "content": Array<{
        "id": string,
        "conversation_id": string,
        "sender_type": string, // The sender type, one of: `CUSTOMER`, `AI_AGENT`, `HUMAN_AGENT`
        // ... remaining fields of a Message as specified in an endpoint above
    }>
}
```

## Socket.IO

Socket.IO is used for real-time, bidirectional communication
between the Partner Portal frontend
and S13 (Partner Consultation Service),
and through A10, S01,
ultimately leads to real-time communication
between the human agent (consultant)
and the customer.

It supports:

- Real-time audio streaming
- Real-time text streaming

Socket.IO is NOT used for:

- CRUD operations
- Message persistence
- History retrieval

Those are handled via REST, like the endpoints above.

### Connection

The client establishes a Socket.IO connection to `/socket.io`

Authentication is done using JWT.

If authentication fails, the server MUST reject the Socket.IO connection.

### Authentication

JWT must be provided via Socket.IO `auth` payload.

Example:

```js
io("/", {
  auth: { token: "<JWT>" }
});
```

### Namespace

Namespaces are intentionally avoided for simplicity.

All events are sent over the default namespace - probably `/`.

### Room Model

Each conversation maps to one Socket.IO room:

```py
room = f"{conversation_id}"
```

That is, room name equals the conversation ID string and is globally unique.

- Client joins exactly one room at a time.
- To join another room, client makes sure to leave the one joined previously, if any.
- Server emits events to corresponding rooms as messages arrive (from human consultant or the other end - the customer).
- Audio and text always belong to a particular conversation.

### Real-time Text Message and General Events Streaming

This is used for:

- notifying customer's text messages to human agents
- system messages

REST `POST AUTH /api/v1/conversations/{conversation_id}/messages` (specified above) is still used for sending text messages from human agents
to customers.

#### Socket.IO Text Event: `new_message`

New text message from the customer
is notified to the human agent.

Server → Client only:

- event: `new_message`
- payload:
  
    ```ts
    {
        "conversation_id": string
        "timestamp": number,    // Unix timestamp in ms (capture time)
        "sender_type": string, // The sender type - here it would be `CUSTOMER`
        "content": string, // e.g. "Xin chào"
    }
    ```

#### Socket.IO General Event: `consultation_request`

A customer is requesting consultation from
huan agent.

Server → Client only:

- event: `consultation_request`
- payload:

    ```ts
    {
        "conversation_id": string,
        "title": string, // e.g. "Tư vấn gói cước"
        "customer_satisfaction": number, // ranging from 1 to 5
        "summary": string // brief summary of the conversation
    }
    ```

#### Socket.IO General Event: `consultation_response`

Human agent acknowledges the consultation request - either
accepting or rejecting it.

Client → Server only:

- event: `consultation_response`
- payload:
  
    ```ts
    {
        "conversation_id": string,
        "accepted": boolean // true if accepted, false if rejected
    }
    ```

#### Socket.IO General Event: `incoming_call`

A customer is starting a voice call
with the human agent.

Server → Client only:

- event: `incoming_call`
- payload:

    ```ts
    {
        "conversation_id": string
    }
    ```

#### Socket.IO General Event: `call_pickup`

Human agent picks up the incoming call.
This also indicates the beginning of a call session.

Client → Server only:

- event: `call_pickup`
- payload:

    ```ts
    {
        "conversation_id": string
    }
    ```

#### Socket.IO Audio Event: `call_end`

End the call session. This is done
by either the human agent or the customer.

Client → Server, or Server → Client:

- event: `call_end`
- payload:

    ```ts
    {
        "conversation_id": string
    }
    ```

### Real-time Audio Streaming

Real-time audio is streamed using **Socket.IO binary messages**.
Each audio message carries a **single fixed-duration PCM frame**.

Audio is unidirectional per event, but the same event structure is used in both directions.

Audio format:

- Encoding: PCM (signed integer)
- Endianness: Little
- Sample rate: 16000 Hz
- Channels: 1 (mono)
- Sample width: 16-bit (int16)
- Container: Raw PCM (no WAV header)

This format is chosen because it is trivial to generate, decode, and play on both browser and backend.

Frame size:
- Each audio frame represents 20 ms of audio.
- Calculation:
    - 16,000 samples/sec × 0.02 sec = 320 samples
    - 320 samples × 2 bytes = 640 bytes per frame
- So, each audio chunk MUST be exactly 640 bytes

Transport Encoding:
- Audio is sent as binary data.
- **NO base64 encoding**
- Socket.IO automatically handles binary frames
- Payload type:
  - Browser: `ArrayBuffer`
  - Python (Flask-SocketIO): `bytes`

Socket.IO events:

#### Socket.IO Audio Event: `audio_start`

Indicates the beginning of an audio stream.

Client → Server, or Server → Client:

- event: `audio_start`
- payload:

    ```ts
    {
        "conversation_id": string
    }
    ```

#### Socket.IO Audio Event: `audio_chunk`

Carries exactly one PCM frame (20 ms).

Client → Server, or Server → Client:

- event: `audio_chunk`
- payload:

    ```ts
    {
        "conversation_id": string,
        "timestamp": number,    // Unix timestamp in ms (capture time)
        "audio": ArrayBuffer    // EXACTLY 640 bytes of PCM data
    }
    ```

Partial PCM frames MUST NOT be sent. The final frame MUST
be padded with silence to 640 bytes, or omitted
entirely before `audio_stop`.

#### Socket.IO Audio Event: `audio_stop`

Indicates the end of the audio stream.

Client → Server, or Server → Client:

- event: `audio_stop`
- payload:

    ```ts
    {
        "conversation_id": string
    }
    ```

### CRITICAL NOTICE

Audio handling here is always in this mode: the client streams fixed-size PCM
frames via Socket.IO.

To stream PCM frames, use the aforementioned
Socket.IO API, with `audio_start`, `audio_chunk`,
and `audio_stop` events.

The following are NOT allowed:

- Sending partial PCM frames
- Persisting streamed audio frames as messages in database.
    Instead, forward the audio chunks immediately and
    discard them.

### Bonus: Client (Browser) Receiving Audio Chunks

1. Receiving audio

    - Upon receiving `audio_chunk`:
      - Extract audio (ArrayBuffer)
      - Interpret it as Int16 PCM
      - Convert to Float32
      - Push into a playback buffer
      - Play via Web Audio API

    - Reference decoding logic (conceptual):

        ```js
        const pcm16 = new Int16Array(audioBuffer);
        const float32 = new Float32Array(pcm16.length);

        for (let i = 0; i < pcm16.length; i++) {
        float32[i] = pcm16[i] / 32768;
        }
        ```

2. Playback

    - Use AudioContext
    - Create an AudioBuffer
    - Write decoded samples
    - Schedule playback slightly in the future (jitter buffer)
    - Clients SHOULD buffer 2–4 frames (40–80 ms) before playback
        to reduce jitter.
    - Conceptual code:

        ```js
        const audioBuffer = audioContext.createBuffer(
        1,
        float32.length,
        16000
        );

        audioBuffer.copyToChannel(float32, 0);
        ```
